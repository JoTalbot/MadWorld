# Инструкции для AI-агентов MadWorld

## Формат ответов

При взаимодействии с пользователем AI-агент должен:

- Использовать **маркированные списки** как основной формат ответа.
- Структурировать информацию подзаголовками и короткими пунктами для удобного чтения.
- Использовать эмодзи умеренно, но заметно, для визуального обозначения статусов и типов информации.
- Для статусов предпочитать понятные маркеры, например:
  - ✅ выполнено
  - 🔄 в работе
  - ⏳ ожидает проверки/CI
  - ⚠️ проблема или риск
  - 💡 улучшение/идея
  - 🚀 следующее действие
- Не превращать ответы в длинные сплошные полотна текста, если информацию можно представить списком.
- Сохранять техническую точность и не жертвовать содержательностью ради форматирования.

## GitHub + Remote Operator

- GitHub является source of truth для кода, workflows и документации.
- Перед существенными изменениями проверяй текущую ветку и HEAD.
- Для серверных операций используй **новый Remote Operator SSH-модуль** через каноническую очередь `.github/remote-operator/COMMANDS.txt`.
- Все AI-агенты MadWorld имеют право использовать Remote Operator для выполнения серверных Bash/SSH-операций, необходимых для диагностики, тестирования, деплоя, обслуживания и проверки проекта.
- Remote Operator предоставляет SSH-доступ к настроенному production Linux-серверу через SSH-учётную запись, GitHub Actions/SSH bridge и установленный на сервере queue executor.
- Агент должен не выполнять SSH-команду самостоятельно вне предусмотренного механизма, а создавать задание в `COMMANDS.txt`, если операция предназначена для Remote Operator.
- Remote Operator намеренно поддерживает произвольные shell-команды без command allowlist. Безопасность обеспечивается SSH-учётной записью, GitHub Secrets, host-key verification и системными правами сервера.
- Короткие операции выполняй в `sync`, длительные — в `async` с polling и timeout.
- Для установленного server-side queue executor новые задания должны добавляться в `COMMANDS.txt`; executor сам выполняет их с lifecycle `PENDING -> CLAIMED -> RUNNING -> DONE | FAILED | TIMEOUT | CANCELLED | INTERRUPTED | INVALID`.
- Проверяй фактический `stdout`, `stderr`, `exit_code`, состояние выполнения и доступный result artifact/record.
- Не утверждай, что операция выполнена, если она не подтверждена фактическим результатом.
- Используй статусы `VERIFIED`, `PARTIALLY VERIFIED`, `NOT VERIFIED`, `NOT EXECUTED`, `FAILED`, `UNKNOWN` там, где это уместно.
- Secrets и приватные ключи никогда не записывать в репозиторий, логи, artifacts, issues или отчёты.
- Не делать force push без явного указания.
- После исправления повторять релевантные проверки и тесты.

## Remote Operator command queue

- Канонический файл очереди Bash-команд: `.github/remote-operator/COMMANDS.txt`.
- **Все новые Bash-команды, которые должны быть выполнены Remote Operator, обязательно дописывать в конец `.github/remote-operator/COMMANDS.txt`.**
- Не перезаписывать, не сортировать и не удалять существующие записи очереди.
- Каждой команде назначать уникальный неизменяемый `COMMAND_ID`.
- Новая команда должна иметь `STATUS: PENDING`.
- Агент не должен самостоятельно выполнять такую команду, если задача предназначена для Remote Operator.
- Только исполнитель Remote Operator переводит команду в `CLAIMED`, затем `RUNNING`, а после завершения в `DONE`, `FAILED` или `TIMEOUT`.
- Уже обработанные команды нельзя автоматически выполнять повторно с тем же `COMMAND_ID`.
- Параллельные агенты могут добавлять разные команды в конец очереди, но не должны изменять активные записи других агентов.
- Сохранять выполненные команды как audit trail.
- Не помещать в очередь пароли, токены, приватные ключи, cookies или другие секреты.
- `.github/remote-operator/COMMAND.txt` больше не использовать для новых команд. Все новые задания помещать только в `COMMANDS.txt`.

## Работа одним батчем

Если пользователь пишет `+`, «делай всё», «одним батчем», «до конца» или аналогичную команду, выполнить весь текущий логически связанный этап: анализ → изменения → тесты → проверка → исправления → повторная проверка → итоговый отчёт.
